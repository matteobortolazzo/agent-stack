# Error Handling

Rules for error classification, sentinel errors, failure visibility, and default-deny behavior across the watch codebase.

## Rules

- When introducing a new sentinel error for detection via `errors.Is()`, add a direct unit test at the package boundary asserting the sentinel is returned and detectable — do not rely on indirect coverage via higher-level integration tests, as a refactor could silently break `errors.Is()` while indirect tests still pass (#412).
- When testing error handling where the same code path can return multiple distinct failure classes, use error-content-specific assertions (e.g., `strings.Contains(err, "specific-marker")`) for each case, not just empty/non-empty checks. A non-empty check alone would pass identically if a regression collapsed multiple classes into the same placeholder string, allowing the tests to silently stop distinguishing between them (#446).
- When extracting or reusing a helper function in a new caller with different error stakes (e.g., from informational use to decision-gating), re-examine the helper's error-handling contract even if the extraction preserved existing behavior and tests—a silent-on-error default acceptable in a low-stakes context may mask errors in higher-stakes decision paths (#560).
- When a diagnostic or collection function calls multiple independent read helpers (image metadata, plugin manifests, logs, container inspection), all helpers must use the same failure-visibility strategy — either all show unknown/unavailable placeholders and append `SeverityWarning` findings on read failure, or all silently omit sections. Mixing patterns makes the report ambiguous: readers cannot distinguish 'read failed' from 'no data to display.' See `Diagnose()` in `watch/internal/sandbox/launcher/diagnose.go` for the `versionOrUnknown` pattern (#572).
- When implementing error-type classification for a code path that can fail in multiple distinct ways (e.g., an `os/exec` command failing either because 'no such container' or 'daemon unreachable'), check the same package for existing classification patterns (e.g., `errors.As(err, &exitErr)`, type assertions on `*exec.ExitError`, or sentinel-error checks) before inventing new error handling. Reusing patterns reduces code divergence and prevents silent classification breakage during future refactors — see `readHomeVolumeFile` in `watch/internal/sandbox/launcher/launch.go` and `containerStartupState` in `diagnose.go` (#572).
- When adding a new parser, validator, or derivation function for a security/safety decision, check its default behavior on malformed/empty/truncated input—does it default permissive or default-deny on error? Before finalizing, grep the file/package for established conventions in similar functions (e.g., `containerHasSharedAgentMount`, `containerStartupState`); if they follow a "default deny" pattern, your new function should too. Deviating silently risks pattern inconsistency that code review may miss, especially when the deviation takes the "safer-looking" but actually-permissive default. In #628, `parseReusePosture` silently returned zero-value (permissive, interpreted as "no host socket") on malformed `docker inspect` output, the only function in `launch.go` to default permissive instead of deny; the inconsistency went undetected until review (#628).
- When a function returns `(value, ok bool)` and is called at multiple call sites within the same logical invariant or comparison (e.g., comparing rank of both current and target stages using `stageRank(current)` and `stageRank(target)`), apply the default-deny discipline uniformly to every call site—not just the one handling external input. It's easy to reason "that side looks reachable by hostile input, so it needs the ok check" and miss the same function's ok discarded on the other side of the comparison. An unregistered/missing value on the unchecked side silently degrades to zero, canceling the default-deny guard on the other, making the entire invariant permissive when only half was intended to be (#636).
- When a helper returns (partial results, error) from concurrent or sequential operations (e.g., `RuntimesWithVolume` querying both docker and podman, returning owners found plus an errors.Join of any query failures), callers must handle both together: appending the error to an error aggregation list and proceeding with the partial results, not treating non-nil error as fatal to using the partial results. One runtime's listing failure doesn't invalidate another runtime's successful query or the action the caller intends to take against it (#629). Write explicit regression tests for this case (e.g., `TestSandboxUpdateAgent_OneRuntimeVolumeQueryFails_HealthyRuntimeStillUpdatedNonZeroExit`) where one runtime's query fails but the other succeeds, to prevent silent regressions where error-return refactors collapse back to treating any error as fully fatal.
- When establishing a security or safety principle for handling one class of malformed/anomalous input (e.g., "missing/unknown data ⇒ treat as stale/unsafe"), systematically audit ALL related malformed-input or anomalous-data classes that should fall under the same principle before finalizing—do not stop at the case the ticket text called out. Examples: if missing timestamps → stale, also audit future/corrupted timestamps and ensure they follow the same principle; if unparseable env var → error, also audit valid-but-huge values (overflow-risking) and bound them before arithmetic. Write explicit test cases for each edge case. In #710, missing timestamps were correctly treated as stale, but future-dated timestamps (which should also be stale) and overflow-risking TTL hours (which should be bounded) were not initially audited, requiring security-review findings and rework (#710).
- When implementing a safety guard or invariant that depends on identifying a critical entity for security purposes (e.g., "never attach the main checkout"), derive that identity from the authoritative system answer (`git worktree list --porcelain`, filesystem stat, container runtime API, etc.), not from caller-supplied parameters or override flags used for testing — the test hook value is valid for initialization only, never for security-critical identity comparisons. A caller-supplied value can be spoofed to bypass the guard; the system's own answer cannot be. Example: `AttachWorktree` validates against `records[0].Path` from `git worktree list --porcelain` (the authoritative repo-wide answer), not against `resolveMainRoot(o.RepoRoot)`, which returns the caller-supplied `--repo` test hook verbatim — a caller could point `--repo` at a linked worktree to disguise the true main checkout and bypass the guard if the override were trusted instead (#688).
- Never write `if err != nil || benignCondition { return PermissiveOutcome }` in any re-verification or safety-gating decision — this pattern silently collapses command error with a legitimate benign condition, violating the error/benign separation principle. Handle them in distinct branches: `if err != nil { return ErrOutcome; }` followed by `if condition { return BenignOutcome; }`. This matters especially when re-verifying a state during a window where intervening operations have happened (e.g., re-checking `HEAD` branch after a network call, re-probing git state after a fetch that could have failed): a probe error must not silently fold into "state is different" (permissive). The pattern is easy to miss when hastily implementing a similar check near an earlier, correctly-written check in the same function. Grep the same function for established error-handling patterns before finalizing (#822).
- When re-purposing an existing data source that was previously used only for best-effort detection (low-stakes: missing items just delay tracking) into a safety-critical or authorization-gating decision (high-stakes: incomplete data causes fail-open), systematically re-audit its completeness guarantees—especially pagination limits, cap-bounded fetches, and truncation handling. Data completeness acceptable for lossy detection can silently fail open in an authoritative use-case: a paginated fetch where stale data within the fetched page could mask newer data on a later page will now make the wrong authorization decision. Guard against truncation by detecting when pagination indicates more data exists beyond what you fetched: treat that as "resolution unknown" and hold with a distinct `truncated` or `unresolvable` reason, never as "complete and safe to merge." Do not collapse the "fetch was truncated" signal into an ordinary "no data" reason—truncation means the verdict is unreliable, not that the state is resolved. A cap-bounded fetch that hits its limit must also fail closed (treat as unknown/incomplete) unless you have already verified that no data beyond the cap can alter the verdict (#850).
- When a classification map or decision gate categorizes multiple processing attempts on the same key into distinct success vs. error buckets (e.g., `probes[key]` tracking whether each plan file parsed successfully), success classifications must always overwrite any previously-recorded error classification for the same key, regardless of processing order — apply first-wins semantics only when comparing classifications of the same kind (success-vs-success or error-vs-error). A naive "first write wins" guard that can lock in an error classification early violates the principle: if a later file succeeds, the gate must reflect that success. This matters especially when the error classification looks "safer" (cautious default-deny) than trying the next entry, because the guard then silently prevents upgrades to the actual winning result (#852). **Scope (#884):** this success-overwrites-error rule applies only to a single processing attempt's own success-vs-error outcome, never to genuine multi-claim ambiguity on the same key — when 2+ distinct entries (any mix of healthy/broken) each independently claim the same key, that is an ambiguity hold, not a first-wins/upgrade scenario, and the classification must reflect the ambiguity rather than either claim's individual outcome. `internal/planfile`'s shared plan-inventory contract (`Inventory.Select`) is the canonical example: a broken duplicate plan file for a ticket that also has a healthy plan is never silently absorbed into the healthy one, superseding the earlier first-wins guard for that specific case.
- When implementing a new function that handles an error class already present in sibling functions within the same file, examine how siblings propagate that error (wrap with `fmt.Errorf` and `%w`, log, silently discard, etc.) and match their strategy rather than choosing independently. Inconsistent error propagation within the same file silently diverges error visibility and diagnostic detail available at the caller boundary — compare `draftFreshness` and `planIsStale` in `watch/internal/pipeline/planfile.go`, both handling `planfile.CommitsBehind` errors (#853).
- When a plan Assumption or specification explicitly describes a write-ordering or failure-handling contract in a sequential operation (e.g., 'a failed label edit must gate/skip the parent close'), verify that the implementation checks the earlier operation's error result before proceeding to the later operation. Do not discard errors from intermediate write operations; use them to gate subsequent operations as documented. This is critical when earlier successful writes must be retained independently of later failures — e.g., a child label succeeds but parent-mutation error must still be visible, and a failed label edit must prevent a subsequent close from permanently sealing the parent with incorrect labels. A close issued after a failed label edit creates an unrecoverable state where the next tick's "already-closed" branch short-circuits before ever touching labels again (#811). Cross-reference plan Assumptions and sequenced-write code paths during implementation review, not just after commit.
- When a data source previously used only for best-effort detection is re-purposed into an authorization-gating decision (#850, above), the generalization also applies one level deeper for a *nested* connection inside the same paginated fetch: a page-level `hasNextPage` proving the outer connection complete does not prove a nested per-item connection (e.g. one PR's `closingIssuesReferences`) is complete too. Treat the nested connection's own truncation as its own distinct gate-worthy verdict (its own reason string), not folded into either "outer complete" or "outer incomplete" — a single overflowing nested item must not be silently absorbed into an otherwise-healthy outer page (#881).
- When adding a new field that must be populated at every failure site within a category (e.g., `FailureClass` at every subprocess error before `recordDecision`), conduct a pre-commit self-check by grepping every `return`/branch that already sets a sibling context field (`Reason`, `Detail`, etc.) in the same function, and verify your new field is set consistently at every one. Sibling branches within the same function are exactly where field-population divergence hides — a branch can appear correct in isolation but incomplete when compared to a structurally-identical parallel branch setting other fields at the same site. This pattern is invisible to early-phase implementation, refactor passes, and even early-round automated review; when the same omission appears in 2+ independent branches within a single PR, multiple independent reviewers converging on the same finding (code, security, silent-failure tracks) suggests this is a recurring pattern worth pre-committing a guard for. Grep the function once before finalizing, not during code review (#886).
- When adding a fail-closed/deny-by-default guard to a multi-branch decision function (e.g., a per-ticket dispatch/reconcile loop or a multi-case gate chain), verify the guard's failure condition can actually be reached via the function's *real* upstream data-flow in production, not just via synthetic test fixtures that hand-construct intermediate state. If one branch's own precondition (e.g., `p != nil` matching a plan found by `ReadPlans`) can never co-occur with the guard's failure condition in production (e.g., when `ReadPlans` returns an empty slice on a directory-read error, making `p == nil` always true when inventory is unverified), the guard becomes correct-looking but practically unreachable, while the actual failure scenario silently falls through to a different, ungated branch and mutates state undefended. Prefer placing a repo/ticket-wide fail-closed gate once at the top of the function so it structurally covers every branch (present and future) rather than threading it into each branch's individual condition. Defense-in-depth guards in individual branches are acceptable as backstops only if the top-level gate actually structurally prevents the unguarded branch from ever being reached with the same condition (#884).
- When refactoring a multi-tier security check (e.g., collapsing nested permission-validation layers), verify that hard-error base-level validations do not silently downgrade to warnings or skip entirely in the new structure. Document which validations are enforcement (reject) vs. detection (warn); a hard rejection for write-permission bits (e.g., `group | other & 0022 != 0`) is a distinct invariant from informational warnings on adjacent permission values. Test the specific boundary condition mentioned in the original code, not just similar-looking values—e.g., if the original rejects 0777 (group/other writable), test that directly rather than testing 0755 (which happens to lack those bits anyway); a test that passes with a safe-looking value doesn't prove the code checks for the unsafe condition. In ticket #1142, a tier-1 hard rejection for `XDG_RUNTIME_DIR` write-permission bits was dropped during refactoring; the AC #2 test case for "0755 warns" passed because 0755 has no write bits for group/other, silently masking the regression until security review (#1142).
- When sanitizing a string for host-terminal output that originates from untrusted/cross-boundary input (container-written marker files, external process output, etc.), use `unicode.IsPrint(r)` for filtering (not ASCII-only predicates like `r < 0x20 || r == 0x7f`) to exclude not just C0 control bytes and DEL but also C1 controls (U+0080–U+009F), Unicode bidi characters (U+202E RLO, etc.), and format characters (U+200B, U+2066–U+2069) that could spoof or manipulate terminal output when written by a compromised container. Additionally, when truncating to a byte-length bound, walk back from the cutoff via `utf8.RuneStart` to find a valid rune boundary, ensuring multi-byte UTF-8 characters straddling the limit are never split mid-encoding. See `sanitizeEventDeliveryMessage` in `watch/internal/sandbox/launcher/diagnose.go` (and its regression tests exercising both the character-filtering and rune-boundary-truncation fixes: #1122) for the correct pattern applied to undelivered-event marker fields crossing the container→host seam. This mirrors the existing `sanitizeDetail` pattern in `watch/internal/babysit/automerge.go` (with its own rune-boundary regression test #854) — a pattern the codebase had already hardened once; searching for similar prior sanitization helpers in the same package before writing new ones prevents reintroducing weaker versions (#1122, #854).
- When a specification or acceptance criterion requires multiple distinct errors to remain independently discoverable (e.g., via `errors.Is` checks or in an errors.Join at a call boundary), never use an error picker function (`firstNonNil`, `errors.Or`, conditional returns) that returns only one error — the picker silently violates the requirement by collapsing multiple errors into a single return value, masking one error completely. Use `errors.Join` instead to preserve all required errors. Critically, a regression test exercising the co-occurrence of both errors in the same execution path is essential — testing each error independently will pass even if the picker silently drops one, because the picker only drops one when both occur together (#927). Document the co-occurrence test case so future refactors don't remove it assuming each error is covered elsewhere.
- When a plan or ticket specifies validating certain fields (e.g., `pr`, `repo`, `agent`) on a message crossing a trust boundary (container→host IPC, privilege-escalation seam, authorization gate), audit and validate *every* field on that message crossing the boundary — do not assume only the AC-enumerated fields need gating. Unvalidated fields on the same message (e.g., `tmux_pane` from container-controlled `$TMUX_PANE`, or `interval` as `time.Duration`) forwarded from untrusted source could enable attacks once that seam is realized. Validate each field's type, range, format, and origin uniformly before use; a single missing validation on an unmentioned field can compromise the entire fail-closed invariant. Design the specification to be explicit: "validate these fields before the seam" should be read as "validate every field before the seam" and verified during code review to ensure all fields crossing the boundary have an explicit validation branch. This is especially critical during planning and review phases — a security auditor will catch missing field validation only if you treat every field uniformly (#1094).
